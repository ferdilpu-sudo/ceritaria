# Direct Video Upload Contract

Status: **Phase 6 server contract implemented and CI verified**  
Updated: **2026-09-27**

## Purpose

Ceritaria accepts direct Android video uploads without placing permanent Cloudflare R2 credentials in the APK.

The trusted boundary is:

```text
Ceritaria Studio Android
  -> Supabase access token
  -> Ceritaria server API
  -> short-lived presigned R2 operation
  -> Android transfers bytes directly to R2
  -> Ceritaria server verifies object
  -> video_assets.status = READY
```

A READY asset is only an uploaded and verified media asset. It is **not** automatically attached to `episodes`. Episode attachment and playback delivery belong to Phase 7.

## Authentication

Every `/api/video-uploads...` route requires a Supabase bearer token and server-side admin authorization.

Permanent R2 credentials remain server-only.

Android never receives:

- R2 access key ID;
- R2 secret access key;
- Supabase service-role credentials.

## Server configuration

Required server-only variables:

```text
R2_ACCOUNT_ID
R2_ACCESS_KEY_ID
R2_SECRET_ACCESS_KEY
R2_VIDEO_BUCKET
R2_MAX_VIDEO_BYTES
R2_SINGLE_UPLOAD_THRESHOLD_BYTES
R2_MULTIPART_PART_SIZE_BYTES
R2_UPLOAD_URL_TTL_SECONDS
R2_UPLOAD_SESSION_TTL_SECONDS
```

The single-vs-multipart threshold and part size are server policy. Android consumes the returned upload mode rather than duplicating these constants.

## Persistent state

Migration `006_video_upload_assets.sql` adds:

```text
video_assets
video_upload_sessions
```

`video_assets` owns the verified object record.

`video_upload_sessions` owns authorization/session state, including multipart layout where applicable.

Existing episode fields remain unchanged in Phase 6. The current public provider contract is still YouTube/Facebook until Phase 7.

## API routes

### Create session

```http
POST /api/video-uploads
Authorization: Bearer <supabase-access-token>
Content-Type: application/json
```

Request:

```json
{
  "episodeId": "<uuid>",
  "mimeType": "video/mp4",
  "sizeBytes": 12345678
}
```

Optional SHA-256 is supported by the server contract.

Response contains:

- canonical `assetId`;
- canonical `sessionId`;
- expiry;
- either SINGLE upload authorization or MULTIPART layout.

### Read recovery state

```http
GET /api/video-uploads/{sessionId}
```

Returns remote session/asset state, expected size, actual size when known, expiry, and multipart layout.

### Authorize multipart part

```http
POST /api/video-uploads/{sessionId}/parts
```

Request identifies one part number. The response returns a short-lived presigned URL and exact byte length for that part.

### Complete multipart upload

```http
POST /api/video-uploads/{sessionId}/complete
```

Android supplies completed `partNumber + etag` values. The server completes the R2 multipart operation and transitions the upload records.

### Finalize and verify

```http
POST /api/video-uploads/{sessionId}/finalize
```

The server performs an R2 HEAD verification before marking the asset READY.

Verification checks the uploaded object against the expected object contract, including size and content type.

If verification fails, the invalid object is deleted best-effort and upload records are failed rather than exposing a false READY state.

### Cancel

```http
POST /api/video-uploads/{sessionId}/cancel
```

Cancels the server session and aborts multipart state where applicable.

## Upload modes

### Single

```text
create session
 -> presigned PUT
 -> finalize
 -> HEAD verify
 -> READY
```

### Multipart

```text
create session
 -> server creates multipart upload
 -> Android asks authorization per missing part
 -> PUT part bytes
 -> persist ETag locally
 -> retry/resume missing parts only
 -> complete multipart
 -> finalize
 -> HEAD verify
 -> READY
```

The maximum multipart part count is 10,000.

## Recovery semantics

The server exposes current upload status so Android can decide whether to:

- treat a remote asset as already READY;
- resume missing multipart parts;
- finish a multipart upload that already transferred all parts;
- restart from a new session when the old session is terminal, invalid, or expired.

Single PUT cannot resume a partial object. If finalization shows that the single object is absent or the session is no longer usable, Android starts a new session.

## Security rules

- Object keys are generated by the server, not supplied by Android.
- MIME type is restricted to `video/mp4` for this contract.
- Maximum file size is server-configured.
- Upload URL lifetime is server-configured and short-lived.
- Session lifetime is server-configured.
- RLS limits upload tables to admins.
- Session ownership is checked by the server.
- Server-side object verification is required before READY.
- Upload completion never publishes an episode.
- Upload completion never replaces the episode's current production video.

## Production smoke checklist

Before enabling R2 episode delivery:

1. apply all video-upload migrations to the target Supabase project;
2. configure R2 server secrets and bucket;
3. verify unauthorized bearer requests are rejected;
4. upload one object below the single threshold;
5. upload one object above the multipart threshold;
6. interrupt multipart transfer and resume missing parts;
7. verify an expired/cancelled session cannot finalize;
8. verify mismatched object metadata does not become READY;
9. confirm Android receives READY with no permanent R2 credentials;
10. leave the episode's current YouTube/Facebook video unchanged until Phase 7 attachment succeeds.

## Phase 7 dependency

Phase 7 must define the public/private delivery strategy for READY assets before extending the public player.

At minimum it must define:

- how an episode references one READY asset;
- how playback receives a usable URL;
- atomic replacement semantics;
- old-asset replacement/cleanup;
- compatibility with existing YouTube/Facebook episodes.
